# ci-gate: a merge gate for the target repository

Generate a GitHub Actions gate that runs the full suite with retries off, enforces changed-line
coverage, ratchets skip markers and suppressions against the base, scans for secrets and audits
dependencies, all behind one required check. Notes for GitLab CI and Azure Pipelines are in §9.

## 1. What the gate runs

`.github/workflows/ci-gate.yml` (first line `# generated by agentic-developer-companion ci-gate: ...`):

| Job | Runs | In Merge OK |
|---|---|---|
| `changes` | `dorny/paths-filter@v4`: `code` is false for Markdown, `docs/**`, `LICENSE*` only | yes |
| `test-<project>` | per project and OS: frozen install, full suite with retries off, report, counts, JUnit publisher, artifacts | yes |
| `coverage-<project>` | PRs: suite with coverage, changed-line coverage (§5) | yes |
| `e2e-<project>` | Playwright projects: browsers, `--fail-on-flaky-tests`, HTML + JUnit upload | yes |
| `ratchet` | PRs: `adc.mjs diff-scope` against the base (§6) | yes |
| `secrets` | gitleaks on the commits of the change, checksum-verified binary | yes |
| `quarantine` | when `tests/quarantine.json` exists: owner, issue, expiry of every entry | yes |
| `audit` | dependency audit per stack | **no** (informational) |
| `agent-verify-<host>` | optional, PRs by coding agents (§7) | **no** |
| `merge-ok` | `if: always()`; fails unless every needed job is `success` or `skipped` | the required check |

Merge OK exports the first test job's `executed`, `passed`, `failed`, `skipped`, `flaky` (also
`workflow_call` outputs) so trends can be charted elsewhere; every project's counts are in its
`adc-counts-<project>.json` artifact. `.github/adc/gate.mjs` is the dependency-free helper the jobs call.

## 2. Scaffold it

```bash
node "$ADC" scaffold ci-gate --json            # dry run: the files and jobs
node "$ADC" scaffold ci-gate --os linux,windows --threshold 80 --write --json
```

| Option | Effect |
|---|---|
| `--os linux,windows,macos` | OS matrix (runner labels such as `ubuntu-24.04` too); default: the OSes the existing workflows use, else Linux |
| `--threshold <0-100>` | Changed-line coverage percentage once enforced (default 80) |
| `--max-flaky <n>` | Flaky tests tolerated before the gate fails (default 0) |
| `--test-cmd "<cmd>"` | The command that runs the whole suite when no runner is detected; its output becomes the report |
| `--for copilot\|claude\|codex\|all` | Adds the agent verify job(s) (§7) |
| `--skill-path <dir>` | The companion vendored in the repo; default: found in `.github/skills`, `.agents/skills`, `.claude/skills` |
| `--write`, `--force` | Write after the user saw the list; replace existing files (backup in `.adc/backups/scaffold/`) |

No runner and no `--test-cmd`: exit 3 (`NO_RUNNER`). Without a vendored copy the jobs fetch the
skill at the pinned tag (`ADC_REF: v<version>`): pin a commit SHA there, or vendor the skill
([install](install.md)). Run `scaffold flake` first if the repository quarantines tests: the gate
then excludes `@quarantine` tests and adds the registry check.

## 3. Branch protection: require only "Merge OK"

A path-filtered workflow that is skipped leaves its required check "Expected" and blocks the merge.
Require **only** the `Merge OK` check in the branch protection rule or ruleset; the real jobs sit
below it and a job skipped by the filter counts as passed. Never add the other jobs as required.

## 4. Full suite, retries off, reports

The test step is the detected runner's command plus the CI flags from the `runners` table in
`assets/templates/ci-gate.tmpl` (retries off, a report under `reports/`):

| Runner | Added in CI | Report (format) |
|---|---|---|
| node:test | `--test-reporter=spec ... --test-reporter=junit --test-reporter-destination=reports/junit.xml` | junit |
| Vitest | `--retry=0 --reporter=default --reporter=junit --outputFile.junit=reports/junit.xml` | junit |
| Jest | `--json --outputFile=reports/jest.json` | jest-json |
| Mocha / Bun | `--retries 0 --reporter xunit ...` / `--reporter=junit --reporter-outfile=...` | junit |
| pytest | `-p no:rerunfailures --junit-xml=reports/junit.xml` | junit |
| Go | `-count=1 -json > reports/go-test.jsonl` | go-test-json |
| Cargo / nextest | `cargo test --no-fail-fast 2>&1 \| tee reports/cargo-test.txt` | cargo-text |
| .NET | `--logger "trx;LogFileName=results.trx" --results-directory reports` | trx |
| Maven / Gradle | `-Dsurefire.rerunFailingTestsCount=0` / none | junit (`target/surefire-reports`, `build/test-results`) |
| RSpec | `--format progress --format json --out reports/rspec.json` | rspec-json |
| Playwright | `--reporter=list,junit`, `PLAYWRIGHT_JUNIT_OUTPUT_NAME=reports/junit.xml` | junit |

`gate.mjs counts` then fails the job when the report is missing, **no test executed**, any test
failed or errored, or more tests were flaky than `--max-flaky`. It writes the step summary table and
`adc-counts-<project>.json` (schema `adc-counts/1`), uploaded as an artifact: download it and pass
it to `clean-run --base-counts <file>` to compare a local run with CI.

## 5. Changed-line coverage

| Runner | Coverage command | Changed lines |
|---|---|---|
| node:test | `--experimental-test-coverage --test-reporter=lcov` | diff-cover on LCOV |
| Jest | `--coverage --coverageReporters=lcov` | diff-cover on LCOV |
| Vitest | `--coverage.enabled --coverage.reporter=lcov` (only with `@vitest/coverage-v8`/`-istanbul`) | diff-cover |
| pytest | `--cov --cov-report=xml:coverage.xml` (only with `pytest-cov`) | diff-cover on Cobertura |
| Go | `go test ./... -count=1 -coverprofile=coverage.out` | `adc.mjs coverage-delta` |

Coverage is **reported first**: the job writes the diff-cover Markdown into the step summary and
warns. Set the repository variable `ADC_COVERAGE_ENFORCE=true` to enforce the threshold
(`ADC_COVERAGE_MIN` overrides it). Other stacks get a next step instead of a job: add the producer
(coverlet → Cobertura → diff-cover for .NET; `cargo llvm-cov --lcov` for Rust; SimpleCov for Ruby)
and copy the `coverage-<project>` job. Without Python, `jest --changedSince=origin/<base>` with a
`coverageThreshold` is the fallback, and it is **approximate (file-level)**: label it so.

## 6. Ratchet, secrets, audit

- **Ratchet**: `node "$ADC" diff-scope --base "origin/$BASE_REF" --json`, then
  `gate.mjs ratchet --report <json> --exit <code>`: fail-severity findings (deleted tests, new skips,
  suppressions, weakened CI) fail the gate and become `::error` annotations; other findings become
  warnings. A diff-scope error (shallow clone, missing base) fails the gate rather than passing.
- **The header rule**: workflows that start with `# generated by agentic-developer-companion ci-gate`
  are the companion's own, so a later `verify` reports edits to them as findings instead of CK-CI
  failures. Keep the header when you adapt a file; never use it on a workflow you wrote yourself.
- **Secrets**: gitleaks 8.30.1 (checksum verified) scans the commits of the change with
  `--redact`; commit `.gitleaks-baseline.json` (`gitleaks git --report-path .gitleaks-baseline.json`)
  when the history holds accepted findings.
- **Audit** (informational): `npm audit --audit-level=high` (pnpm, yarn variants), `pip-audit`,
  `cargo audit`, `govulncheck`, `dotnet list package --vulnerable --include-transitive`,
  `bundle-audit`. Read its output on every PR; it never blocks Merge OK.

## 7. Agent verify job (optional)

`--for copilot|claude|codex` adds `agent-verify-<host>`, which runs only on PRs whose author is in
the repository variable `ADC_AGENT_AUTHORS` (default `Copilot,copilot-swe-agent[bot]`), installs the
skill at user scope, runs the companion's `verify` headless and posts the rendered ledger as a PR
comment. Secrets: `COPILOT_GITHUB_TOKEN` (Copilot CLI, `copilot -p ... --trust-folder --no-ask-user
--allow-tool 'shell(node:*)' --allow-tool 'shell(git:*)'`), `ANTHROPIC_API_KEY` (`claude -p
"/agentic-developer-companion verify origin/$BASE_REF --yes"`), `OPENAI_API_KEY` (`codex exec -s
workspace-write`). These jobs cost money and are informational, never part of Merge OK.

## 8. The gate helper `.github/adc/gate.mjs`

Node 24, no dependencies; it loads the companion's report parsers through `ADC`. Exit `0` pass,
`1` the gate fails, `2` usage. Run it locally to debug a red job:

```bash
ADC="$PWD/.github/skills/agentic-developer-companion/scripts/adc.mjs" node .github/adc/gate.mjs counts --format junit --report 'reports/*.xml' --max-flaky 0
node .github/adc/gate.mjs ratchet --report diff-scope.json --exit 1
node .github/adc/gate.mjs coverage --report coverage-delta.json
node .github/adc/gate.mjs quarantine --registry tests/quarantine.json --today 2026-10-26
```

`ratchet`, `coverage` and `quarantine` need no `ADC`. Both `scaffold ci-gate` and `scaffold flake`
write the same file; the second one reports it `unchanged`.

## 9. GitLab CI and Azure Pipelines

Not generated. Port the same structure by hand:

- One always-present final job that needs every gate job (GitLab `needs:` with `rules: - when:
  always`; Azure a final stage with `dependsOn` and `condition: always()` that fails on any failed
  dependency). Path filters (`rules: changes:`, Azure `paths` triggers) sit on the jobs below it.
- The same commands: frozen install, the test command and flags of §4, `node .github/adc/gate.mjs
  counts ...`, `node "$ADC" diff-scope --base origin/$BASE --json` + `gate.mjs ratchet`, gitleaks,
  diff-cover. Publish JUnit (`artifacts:reports:junit` / `PublishTestResults@2`).

## 10. Guidance-only mode (no Node)

Write the workflow by hand from §1-§6: the `changes` job, one test job per project with the frozen
install and the runner flags of §4, a JUnit publisher, `diff-cover <report> --compare-branch=origin/<base>`,
gitleaks, the audit job outside the aggregate, and the `merge-ok` job with `if: always()` that fails
on any result other than `success` or `skipped`. Start the file with the ci-gate header line only if
you keep the generated structure, and say "guidance-only mode" in the summary.

Post: the files written, the jobs and which are required (Merge OK only), the coverage threshold
and whether it is enforced, the repository variables and secrets to create, and the pinned skill
reference or vendored path.
