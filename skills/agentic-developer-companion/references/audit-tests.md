# audit-tests: test quality of an agent-made change

Judge whether the tests in a change prove anything. Every dimension is a **yes / no /
unknown** question answered with a `file:line` citation; the script computes every score
from your answers. Never estimate a score, never answer without opening the cited line, and
prefer `unknown` to a guess.

## 1. Scope and inputs

- **Paths given** (`audit-tests tests/limiter.test.ts`): audit those test files.
- **No paths**: audit the test files the change adds or modifies against the base (`--base`,
  default chain in [verify](verify.md) §1), uncommitted and untracked files included.
- **Regression tests** (the change fixes a bug): also prove red-green (§4). Ask for the bug
  or issue when the change does not name it; headless runs record `unknown` instead.

## 2. Run it

Reuse the ledger of a `verify` run on the same snapshot (`evidence status --json` shows it
and whether it is `stale`); otherwise create one. Write every intermediate file into the
ledger's folder, the ledger path without `.json` ([verify](verify.md) §1).

```bash
L=$(node "$ADC" evidence init --json | node -e "let s='';process.stdin.on('data',d=>s+=d).on('end',()=>process.stdout.write(JSON.parse(s).ledger))")
D="${L%.json}"; mkdir -p "$D"
node "$ADC" detect --json > "$D/detect.json"
node "$ADC" diff-scope --json > "$D/diff-scope.json";            node "$ADC" evidence add "$D/diff-scope.json" --ledger "$L"
node "$ADC" clean-run --red-green tests/limiter.test.ts --json > "$D/clean-run.json"; node "$ADC" evidence add "$D/clean-run.json" --ledger "$L"
node "$ADC" coverage-delta --json > "$D/coverage.json";          node "$ADC" evidence add "$D/coverage.json" --ledger "$L"
node "$ADC" mutation-scope --budget 10 --json > "$D/mutation.json"; node "$ADC" evidence add "$D/mutation.json" --ledger "$L"
node "$ADC" flake-probe --times 5 --tests tests/limiter.test.ts --json > "$D/flake.json"; node "$ADC" evidence add "$D/flake.json" --ledger "$L"
```

```powershell
$L = (node $ADC evidence init --json | ConvertFrom-Json).ledger
$D = $L -replace '\.json$', ''; New-Item -ItemType Directory -Force $D | Out-Null
node $ADC diff-scope --json | Out-File -Encoding utf8 "$D/diff-scope.json"; node $ADC evidence add "$D/diff-scope.json" --ledger $L
node $ADC clean-run --red-green tests/limiter.test.ts --json | Out-File -Encoding utf8 "$D/clean-run.json"; node $ADC evidence add "$D/clean-run.json" --ledger $L
```

In PowerShell always write through `Out-File -Encoding utf8` (Windows PowerShell's `>` writes
UTF-16). Repeat the pattern for `coverage-delta`, `mutation-scope` and `flake-probe`. To
reuse the newest ledger instead of creating one, use `evidence status` in place of
`evidence init` in the first line.

- `--red-green` takes comma-separated `file` or `file::test name` entries (only the new
  regression tests). Without new regression tests drop the option.
- `mutation-scope` and `flake-probe` cost time: skip them for a quick audit and answer the
  matching questions `unknown`. A missing mutation tool is `skipped`, not a failure.
- Read each JSON before answering; the fields you need are named in §3–§5.

## 3. The questions

Answer each built-in question once per audit, citing the line that decides it (a test line,
or the source line a test misses). `pass_if` is the answer that counts as passing.

| Id | Question | pass_if | How to decide; what to cite |
|---|---|---|---|
| `AT-NO-ASSERT` | Does any changed test lack an assertion? | no | a test body without `expect(`, `assert`, `t.Error`/`t.Fatal`, `assert_eq!(`, `Assert.`, `should`; a snapshot assertion counts only if the snapshot was reviewed. Cite the test's first line |
| `AT-MIRROR` | Do assertions mirror the implementation (expected values computed by the code under test)? | no | `expect(add(a, b)).toBe(a + b)`, expected values produced by calling the function or copying its formula, golden files regenerated by the change. Cite the assertion |
| `AT-EXCEPTION-ONLY` | Does any test only check that no exception is thrown? | no | `expect(() => f()).not.toThrow()`, `assert f() is not None`, `if err != nil { t.Fatal }` as the only check. Cite it |
| `AT-MOCK-DOMINATED` | Is any test mock-dominated (mocks the unit under test, or the mock earns no assertions)? | no | `jest.mock('../src/limiter')` inside `limiter.test`, `@patch` of the function under test, assertions only on `toHaveBeenCalled`/`assert_called_once`, more mocks than behavioral assertions. Cite the mock |
| `AT-TAMPER` | Were tests deleted, skipped, weakened or excluded from discovery? | no | `diff-scope.json` `findings[]` for CK-TEST-DEL, CK-SKIP, CK-ASSERT, CK-TEST-CFG and `counts` (before/after); a waived finding still answers yes. Cite the finding's `file:line` |
| `AT-RED-GREEN` | Does each new regression test fail with an assertion on the base and pass on the snapshot? | yes | `clean-run.json` `red_green.status` (`pass` → yes) and `pairs[]`; omit the question when the change adds no regression test. Cite the test |
| `AT-BEHAVIOR` | Do the tests exercise the changed behavior (branches, error paths), not just the changed lines? | yes | `coverage.json` `uncovered[]` and `untested_branches[]`, plus reading the changed code for error paths and boundaries. Answering no: cite the untested source line |
| `AT-RETRY` | Were in-source retries added? | no | CK-RETRY findings; `jest.retryTimes`, `@pytest.mark.flaky`, `test.describe.configure({ retries })`, `--reruns` in pytest config, `retries` in `.config/nextest.toml`. Cite it |
| `AT-ORDER` | Do tests depend on order, wall-clock time, network or shared state? | no | module-level mutable state, `Date.now()`/`time.time()` without a fake clock, real HTTP, `sleep`, unseeded randomness; `flake.json` `suspect_tests[]`. Cite it |

Rules the script enforces: a `yes`/`no` without a citation, or with a citation that does
not exist in the ledger's snapshot, is **rejected** and counts as unknown; answers are
`yes`, `no` or `unknown` only. Add your own questions with `"pass_if": "yes"|"no"` and a
`"dimension"` when the code needs them (for example "Does the property-based test bound
its inputs?").

## 4. Red-green proof

A new regression test proves the fix only if, in a base worktree with **only the new test
files** copied in, the named test **executes** (it is in the report) and fails with an
**assertion failure**, and the same test id **passes** in the snapshot. `clean-run
--red-green` does exactly this and records CK-REDGREEN with both report paths
(`red_green.base_report`, `red_green.head_report`, under `.adc/cache/runs/`).

| `red_green.reason` | Meaning | What to do |
|---|---|---|
| (status `pass`) | proven | answer `AT-RED-GREEN` yes |
| `NOT_RED` | the test passes on the base: it does not reproduce the bug | rewrite it to assert the buggy behavior's correct outcome |
| `WRONG_FAILURE_KIND` | the base run fails with an error (import, compile, collection), not an assertion | test through an API that exists on the base, or move the new symbol behind it |
| `NOT_EXECUTED` | the named test is missing from the base report | fix the `file::name` spelling or the runner's test filter |
| `NOT_GREEN` | the test does not pass in the snapshot | the fix is incomplete; report it, do not weaken the test |
| `NO_TEST_IDS`, `NO_RUNNER`, `TEST_FILE_NOT_IN_SNAPSHOT` | could not verify | give the runner (`--runner`) or the right path; the check stays `unverified` |

CK-REDGREEN is never waivable. A failing proof is a `fail` in the ledger.

## 5. Behavior coverage, mutation, flakiness

- **Coverage of behavior, not lines.** `coverage-delta` gives `pct` of changed executable
  lines, `uncovered[]` and `untested_branches[]` (`file`, `line`, `covered`/`total`
  branches). `precision: file` means the report could not be mapped to lines: say
  "approximate". Use coverage to find the branches to ask about.
- **Mutation** (`mutation-scope`): `score` and `survivors[]` on the changed files only. A
  surviving mutant in changed code is a concrete rewrite suggestion: name the mutant and the
  assertion that would kill it.
- **Flakiness** (`flake-probe`): `runs`, `shuffle` (false when the runner cannot shuffle),
  `seeds[]`, `failures[]`, `suspect_tests[]`. A test that fails only in some seeds is
  order-dependent; one that fails at random is timing-, network- or state-dependent.
  Newly added in-source retries are a finding even when the probe passes.
- Two runner behaviors hide flakiness: **cargo-nextest counts a flaky pass as success** by
  default, and **pytest-rerunfailures masks failures** once `--reruns` is configured. Call
  both out when the project uses them.

## 6. Score and record

Write the answers to `$D/audit-answers.json`:

```json
{ "kind": "audit-tests",
  "answers": [
    { "id": "AT-NO-ASSERT", "answer": "no", "citation": "tests/limiter.test.ts:12" },
    { "id": "AT-MOCK-DOMINATED", "answer": "yes", "citation": "tests/limiter.test.ts:3",
      "note": "jest.mock('../src/limiter') replaces the unit under test" },
    { "id": "AT-BEHAVIOR", "answer": "no", "citation": "src/limiter.ts:57",
      "note": "the window-reset branch is never taken" },
    { "id": "AT-ORDER", "answer": "unknown" }
  ] }
```

```bash
node "$ADC" evidence score "$D/audit-answers.json" --ledger "$L" --add --json
node "$ADC" evidence finalize --ledger "$L"
node "$ADC" evidence render --short --ledger "$L"
```

`evidence score` returns `totals` (passed, failed, unknown, rejected, `score`, `coverage`),
per-dimension scores and the rejected answers with their reason (`NO_CITATION`,
`BAD_ANSWER`, an invalid citation). `--add` records **CK-MOCK** (soft: failed answers are
findings, never a `FAIL` on their own); exit 1 when any answer fails. Fix rejected answers
and score again rather than arguing with the result.

## 7. Output to produce

1. The answer table: question, answer, citation, one-line reason; rejected answers marked.
2. The tampering summary from CK-TEST-DEL / CK-SKIP / CK-ASSERT / CK-TEST-CFG with the
   before/after counts.
3. Red-green result per regression test with both report paths.
4. Concrete rewrite suggestions, one per failed answer or surviving mutant: file, line,
   what to assert instead (for example "assert the 429 status and the `Retry-After` header,
   not that `limiter.check` was called").
5. The `evidence render --short` summary and the scores exactly as the script printed them.

Do not edit tests during the audit: suggest the rewrite, or switch to `regress` when the
user asks you to write the missing test.

## 8. Manual fallbacks (guidance-only mode)

Without Node, take `BASE` and `SNAP` from [verify](verify.md) §7.1 and run:

| Step | Commands |
|---|---|
| Changed test files | `git diff --name-status -M $BASE $SNAP` filtered by the test globs (`**/*.{test,spec}.*`, `test_*.py`, `*_test.go`, `src/test/**`, `spec/**`) |
| Tampering | steps 2-4 of [failure modes](failure-modes.md) §4 |
| Red-green | [regress](regress.md) §5 manual fallback: only the new test files in a base worktree must fail by assertion, then pass in the snapshot (`npx vitest run <file>`, `pytest <file>::<name>`, `go test -run <Name> ./pkg`) |
| Coverage | the runner's coverage flag (`npx vitest run --coverage`, `pytest --cov --cov-report=xml`, `go test -coverprofile=c.out ./...`), then `diff-cover coverage.xml --compare-branch=$BASE` |
| Mutation | `npx stryker run --mutate <files>`, `dotnet stryker --since:<base>`, `cargo mutants --in-diff <diff>`, `mutmut run` (POSIX only) |
| Flakiness | repeat commands of [flake](flake.md) §1 |

Write the answer table into the guidance-only ledger ([verify](verify.md) §7) and state that no
script computed a score.

## 9. Limits

Mock-domination, mirrored and weak assertions can be argued either way: cite, explain, and let
the ratchet and the reviewer decide. A red-green proof shows the test detects *this* bug, not
that the fix is complete.
